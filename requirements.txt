## What the agent does
Reads customer payment records → detects which collection stage each invoice is at
→ generates personalized messages via LLM → sends via Email/WhatsApp → logs every
interaction → deduplicates so no message is ever sent twice for the same stage.

## Tech Stack
- Language: Python 3.11
- Scheduler: APScheduler 3.10.4 (BlockingScheduler, daily cron at 09:00)
- LLM: Groq API, model llama-3.3-70b-versatile (gsk_ key)
- Email: smtplib + Gmail SMTP (port 587, STARTTLS, App Password)
- WhatsApp: Twilio sandbox (production needs verified WhatsApp Business Account)
- Data (POC): CSV + SQLite
- HTTP client: httpx
- Env management: python-dotenv
- Testing: pytest with conftest.py shared fixtures

## Key Design Decisions (defend these to your lead)
1. One row per invoice in CSV (not per customer) — supports multiple invoices per customer
2. invoice_ref = f"{customer_id}_{due_date}" — synthetic unique key, no schema change needed
3. Stage detection: find most recent applicable unsent stage (reversed iteration).
   If agent was offline 5 days, fires most relevant stage, not oldest stale one
4. INSERT OR IGNORE on invoice_stage_tracker — DB-level dedup guarantee, not app-level
5. LLM uses SUBJECT:/BODY: delimiters, not JSON — JSON breaks on multiline text from LLMs
6. temperature=0.4 for Groq — consistent professional tone, slight variation per customer
7. Graceful degradation: LLM failure → template fallback; send failure → logged, retried next cycle
8. fresh_db fixture in conftest.py only — single source of truth, applies to all test files
9. DB_PATH overridable via COLLECTION_DB_PATH env var — enables test isolation without
   touching production DB

## Collection Stage Rules
| Stage   | Condition              |
|---------|------------------------|
| pre_7   | 7 days before due date |
| pre_3   | 3 days before due date |
| pre_1   | 1 day before due date  |
| post_1  | 1 day overdue          |
| post_7  | 7 days overdue         |
| post_15 | 15 days overdue        |
| post_30 | 30+ days (escalation)  |

## customers.csv schema
customer_id, customer_name, email, phone, amount_due, currency,
due_date (YYYY-MM-DD), preferred_channel (email/whatsapp), risk_tier (low/medium/high)

## SQLite schema
communication_log: id, customer_id, invoice_ref, stage, channel, status,
                   message_text, sent_at, error_detail
invoice_stage_tracker: customer_id, invoice_ref, stage, completed_at
                       PRIMARY KEY (customer_id, invoice_ref, stage)

## Known Limitations / Flagged for Production
- Twilio WhatsApp sandbox requires each recipient to manually send join message
- LLM occasionally writes [Your Name] placeholder — system prompt patched with
  "Sign off as: Collections Team, Insignytics"
- CSV is flat file — no concurrent write safety
- No retry queue — failed sends only retry on next scheduler cycle
- No authentication or API layer — direct Python execution only
- Scheduler runs in single process — no HA/failover
